# Agent Instructions

- This is a NixOS flake using Den’s dendritic layout. `flake.nix` uses `import-tree` to auto-import `modules/`, which holds framework, schema, host, and quirk plumbing. `aspects/` is the canonical home for configuration aspects. Inspect the existing layout before suggesting where configuration belongs, and never edit generated files such as `flake.lock` or `devenv.lock` by hand.
- Aspect discovery is implemented by `modules/aspects.nix`, not Den itself: it scans `aspects/` during evaluation and registers each file or directory as `den.aspects.<path>`. A name may be a file or a directory, not both. A directory with `default.nix` uses that file as its aspect; a directory without one becomes an aspect that includes all of its subaspects.
- The aspects framework is effectively final. Future framework changes should normally only add utilities to the generated `aspect-utils` interface; do not redesign the aspect import/discovery mechanism without a concrete requirement. Directory aspects can use `aspect-utils.includes-all-subaspects`, `includes-all-subaspects-except`, and `self` for hierarchical composition, and any aspect can fan out to every user of a host with `provides.to-users`.
- The agent's role in this repository is analysis-only: explain the flake, trace configuration behavior, identify risks, and propose changes. Do not write code or Nix configuration, create patches, or commit changes unless the user explicitly requests a repository documentation or configuration change.
- `flake.nix` is hand-written (it was previously generated by `flake-file`). Edit it directly and update `flake.lock` with `nix flake update` or `nix flake lock`; the `nix run .#write-flake`, `write-inputs`, and `write-lock` commands no longer exist. The flake takes a `deploy-rs` input in addition to the Den, nixpkgs, home-manager, impermanence, and nix-index inputs.
- Host definitions are in `modules/hosts.nix`: `archer` and `hierophant` on `x86_64-linux`, and `thief` on `aarch64-linux`. A host's aspect defaults to `den.aspects.<host>`, so its hardware and host-specific settings belong in `aspects/<host>.nix` and the filename must match the host key. Shared host-level includes are configured in `modules/schemas/host.nix`, and shared defaults in `modules/defaults.nix`.
- Impermanence lives in `aspects/impermanence/`: `default.nix` imports the impermanence modules, makes `/persistent` needed for boot, declares the base system and home persistence paths, and aggregates `persist` declarations from included aspects; `diff.nix` adds the `impermanence-diff` and `impermanence-home-diff` helpers for finding files not preserved across reboots. The initrd deletes and recreates the Btrfs `root` subvolume on every boot (using `/dev/disk/by-label/nixos`), so anything not declared persistent is intentionally ephemeral. `/etc/nixos` itself is persisted, which is what makes the deploy-time `git pull` meaningful.
- `persist` is a Den quirk registered in `modules/quirks.nix`, not a normal NixOS option or separate aspect. Use `persist.directories`, `persist.files`, `persist.home.directories`, and `persist.home.files` in aspects; the impermanence aspect aggregates these into system and Home Manager persistence. Be careful with paths and directory attribute sets because they directly control what survives the root rollback. `caddy-configs` is the other registered quirk; service aspects use it to contribute Caddy virtual hosts.
- Deployment uses `deploy-rs`. `modules/deploy.nix` generates `flake.deploy.nodes` from `config.den.hosts`, so all three hosts are deployable. Each node has a `config-sync` profile (as `anton`) ordered before the `system` profile (as `root`); `config-sync` runs `git -C /etc/nixos pull --ff-only` so the target's persisted checkout matches the deployed revision. Deploy only clean, pushed revisions and keep target checkouts clean, otherwise the fast-forward fails. `remoteBuild = true` is global, which is required for the aarch64 `thief` host unless a builder is available.
- Each node's `groups` are all the *other* hostnames, so `deploy --groups <current-host>` selects every node except the one running the command. `scripts/common/fleet` implements this as `deploy --groups (string trim < /etc/hostname) /etc/nixos`; arguments passed to `fleet` are forwarded to `deploy` unchanged. Run `fleet` from the devenv shell to update all other hosts, or `deploy .#<host>` for an explicit target; plain `deploy .` still includes the current host.
- Deploy-rs needs non-interactive root on the targets. `aspects/shell/sudo.nix` disables `security.sudo`, enables `run0` with the sudo shim and `wheelNeedsPassword = false`, and `aspects/nix/default.nix` sets `nix.settings.trusted-users = ["@wheel"]` so `nix copy` is allowed. Both are root-equivalent; do not widen `wheel` casually. Every target hostname must resolve from the deployer and be present in the deploy user's `~/.ssh/known_hosts` (persisted by the SSH aspect). Deploy-rs uses the names in `deploy.nodes.*.hostname` for both SSH and `nix copy`.
- NetBird DNS: `aspects/ssh/netbird.nix` runs the `wl0` client, and `aspects/networking.nix` enables `systemd-resolved` with `networking.networkmanager.dns = "systemd-resolved"` so NetBird can configure per-link DNS. Peer names are `<peer>.netbird.cloud`, and `netbird.cloud` is installed as a search domain, so `resolvectl query archer` resolves the FQDN while `/etc/hosts` still wins for the local hostname. NetBird's resolver listens on port 5053 and relies on port-53 DNAT, so a `:5053` listener is normal. Tools that ignore search domains (`dig`, `host`) will not resolve bare hostnames; use `resolvectl` or `getent`.
- Validate changes with `nix flake check --no-build --no-write-lock-file`; at the current revision it passes and evaluates `nixosConfigurations.archer`, `nixosConfigurations.hierophant`, and `nixosConfigurations.thief`. The non-standard `denful` and `deploy` outputs produce `unknown flake output` warnings but do not fail the check, and the aarch64 configuration is skipped unless `--all-systems` is used. Use `nix eval .#deploy.nodes` to inspect the deployment topology and `nix build .#nixosConfigurations.<host>.config.system.build.toplevel` for a full build; the flake defines no custom `checks`, `apps`, or `packages`.
- Secret material must be encrypted with `git-crypt` before it is stored in the repository. Encrypted `git-crypt` ciphertext may also be stored in the Nix store; because deploy-rs copies closures to every target, assume each host can read it. Never commit or expose the git-crypt key, and never decrypt, print, replace, or expose secret contents. Secret paths include `*.secret`, `*.secret.*`, and files below `*.secret/`, as matched by `.gitattributes`.
- No CI, pre-commit hooks, or automated format/lint/test checks are configured. `devenv.nix` provides a development shell with `alejandra`, `stylua`, `lua-language-server`, and `fish-lsp`, and generates scripts from `scripts/common/` plus `scripts/<hostname>/` (the host directory is selected impurely from `/etc/hostname`). The second line of each script declares runtime packages as `# pkg1;pkg2`; for example `scripts/common/fleet` uses `# fish;deploy-rs`. Formatting and linting are not enforced.
